🤝 Quy trình FE-BE API Handshake 5 Bước (shared_contracts)
SSOT Contract-First

Được quy định trong plugins/shared_contracts/api_handshake_protocol.md. FE không bao giờ tự bịa API hay đoán mò. Khi thiếu endpoint, quy trình Handshake sau được tự động kích hoạt:

1

Phát hiện GAP & Dự thảo Schema (DRAFT_BY_FE)

Spec Writer (FE) phân tích tính năng, nhận diện endpoint chưa tồn tại trên Server. Xuất file hợp đồng nháp: contracts/drafts/<feature>_api.json và contracts/drafts/api_gap_report.md.

2

Thẩm định Kỹ thuật BE (IN_BE_REVIEW & APPROVED_BY_BE)

Spec Writer & Planning (BE) tiếp nhận contract draft, đối soát tính khả thi với Database Schema, Authentication và Performance. Phê duyệt trạng thái sang APPROVED_BY_BE.

3

Cung cấp Mock Server / Swagger (READY_FOR_MOCK)

BE tạo Mock URL hoặc mock data fixture theo schema đã chốt. FE Coder ngay lập tức có thể triển khai Data Source & Cubit với mock mà không bị block.

4

BE Code & Deploy Staging (LIVE_DEPLOYED)

BE Coder triển khai code controller, repository, DB migration và unit test. Deploy endpoint thật lên môi trường Dev/Staging.

5

Tích hợp & Đóng Hợp đồng (VERIFIED_CLOSED)

FE Tester & Coder chuyển Data Source từ Mock sang Live Endpoint. Chạy kiểm thử End-to-End, xác nhận dữ liệu chính xác và đóng Ticket Handshake.

🧪 1. Developer Unit Testing (Con Coder)
Tầng Development

Được thực hiện trực tiếp bởi Code Writer trong quá trình viết code từng Phase, và được thẩm định bởi Code Reviewer.

Trách nhiệm & Phạm vi:

  • Đối tượng kiểm thử: Từng hàm, từng Usecase, Model Mapper, và State transitions trong Cubit/BLoC.
  • Nguyên tắc cốt lõi: Tuân thủ cấu trúc AAA (Arrange - Act - Assert), Mock toàn bộ dependency bằng mocktail.
  • Self-Check bắt buộc: Coder phải tự chạy flutter test trong terminal. Nếu có test fail, Coder tự sửa trước khi gửi cho Reviewer.
  • Reviewer Audit: Reviewer đánh giá tính khách quan của các test cases Coder tự nghĩ ra, bổ sung các edge cases thiếu sót.

Templates hỗ trợ:

usecase_test.dart.tpl • mapper_test.dart.tpl • cubit_test.dart.tpl
🛡️ 2. Independent QA Verification (Test Runner)
Tầng Acceptance

Được thực hiện độc lập bởi Test Runner sau khi tất cả các Phase code đã hoàn tất.

Trách nhiệm & Ranh giới:

  • Nguồn Chân Lý (SSOT): brief.md (Scope In/Out) và requirements.md (BDD Gherkin, Acceptance Criteria AC-NN).
  • Độc lập hoàn toàn với Planning: Không bao giờ dùng implementation_plan.md làm căn cứ nghiệm thu để tránh bias.
  • Toàn vẹn hệ thống: Chạy bộ kiểm thử toàn diện: Flutter Unit Tests, Widget Tests, Integration Tests, và flutter analyze.
  • Defect Remediation Loop: Nếu phát hiện bất kỳ sai lệch nào, Test Runner tạo Defect Report gửi ngược lại bắt Coder sửa cho tới khi PASS 100%.

Báo cáo xuất ra:

verification_report.md • defect_remediation_report.md
⚖️ So Sánh Ranh Giới: Developer Unit Test vs Independent QA
Strict Boundary
Tiêu chí Developer Unit Testing (Coder & Reviewer) Independent QA Verification (Test Runner)
Chủ sở hữu Code Writer viết, Code Reviewer thẩm định & audit Test Runner (QA) độc lập hoàn toàn
Thời điểm thực hiện Ngay trong lúc viết code của từng Phase slice Sau khi toàn bộ code của feature đã xong và được Reviewer duyệt
Căn cứ đối chiếu (SSOT) DoD trong task.md và implementation_plan.md brief.md (In/Out Scope) và requirements.md (BDD Criteria)
Mục đích chính Bảo đảm code chạy đúng logic nội tại, không bị Null/Crash, coverage cao Bảo đảm tính năng thỏa mãn đúng nhu cầu nghiệp vụ, không thừa, không thiếu
Quyền sửa code Có (Coder sửa logic, Reviewer sửa docstring/comment) Không (Read-Only 100%), chỉ tạo report bắt Coder sửa
