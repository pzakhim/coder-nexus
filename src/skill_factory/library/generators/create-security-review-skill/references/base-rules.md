# Base Rules — Security Review (`SR1`–`SR14`, Mandatory Compliance)

All rules below (`SR1`–`SR14`) are **mandatory compliance** across every generated `security-review` skill (never dropped as `"not adopted"`).

| ID | Rule | Why | Target Reference |
|---|---|---|---|
| `SR1` | **Triggered Scope, Fixed Revision & Deterministic Coverage Ledger (`COVERED` / `UNCOVERED`)**: Run on changes matching the security triggers; audit the exact handoff revision (`HEAD` SHA) read-only; enumerate every changed entrypoint, query, job, and trust-boundary unit in a **Coverage Ledger** so zero in-scope units are skipped (`0` `UNCOVERED` units required before `APPROVED`). | Prevents AI auditors from skimming diffs or overlooking secondary entrypoints/background jobs. | `01` |
| `SR2` | **Per-Change Threat Model (STRIDE-lite)**: Document Assets, Actors (roles, anonymous, cross-tenant actors), Entry Points, Trust Boundaries crossed, and applicable STRIDE failure modes in 5–10 lines tailored to the diff. | A focused 2-minute abuse analysis catches multi-step logic flaws that static checklists miss. | `01` |
| `SR3` | **Authorization Matrix (`Role × Environment × Action × Object`)**: For every changed operation, map `Role × Environment × Action × Object (own / other tenant / other owner)` → expected `Allow / Deny (401/403/404)` and cite the verifying test or code path. | Broken Object/Function Level Authorization (BOLA/IDOR & BFLA) hides in unverified matrix cells. | `01` |
| `SR4` | **Data-Scope Isolation Across All Channels**: Verify that every changed DB query, cache key, file path, background job, realtime stream, and export binds the verified caller's scope (`tenant_id` / `org_id` / `owner_id`) from the auth context — never from client payload fields. | A single unscoped query or cache key leaks cross-tenant data. | `01` |
| `SR5` | **Injection, Deserialization & Mass Assignment**: Audit all dynamic query/command/path/template construction, deserialization calls, and request DTO bindings (`extra="forbid"` / strict allow-lists). | Untrusted input reaching an interpreter or unguarded entity attribute turns data into control flow. | `02` |
| `SR6` | **Client & UI Boundary Risks**: Audit untrusted HTML/markdown rendering (XSS), deep-link/redirect target validation, client-side token/secret storage, CSWSH/CSRF origin checks, and UI-only permission gates lacking server enforcement. | Client runtimes (browsers, mobile apps, desktop clients) are fully attacker-controlled. | `02` |
| `SR7` | **Secrets & Personal Data Protection**: Scan code, config, test fixtures, logs, exception envelopes, and commit diffs for hardcoded secrets, tokens, or PII leakage. | Leaked credentials or PII in Git history and logs persist across clones and aggregators. | `02` |
| `SR8` | **Outbound Network Calls & File Handling**: Audit user-influenced URLs for SSRF (scheme/host allow-list, private IP block, redirect policy, explicit timeouts) and file uploads/downloads (size cap, MIME/magic-byte check, path traversal, non-executable storage). | Unvalidated URLs and file streams are primary pivot points into internal infrastructure. | `02` |
| `SR9` | **Supply-Chain & Dependency Audit**: For every added or upgraded dependency in the diff, verify necessity, maintenance health, lockfile pinning, and known CVEs using the workspace's vulnerability scanner. | Vulnerable or typosquatted packages compromise the runtime without code changes. | `02` |
| `SR10` | **Cryptography & Authentication Lifecycle**: Verify standard platform cryptographic primitives, CSPRNG usage, password hashing work factors, token/ticket TTLs, revocation checks, and constant-time signature comparisons. | Weak primitives, predictable tokens, or non-expiring sessions defeat upstream access controls. | `02` |
| `SR11` | **Adversarial Source-to-Sink Disproof & 3-State Classification (`CONFIRMED` / `PLAUSIBLE` / `REJECTED`)**: Every candidate vulnerability must first undergo an **Adversarial Disproof Pass** — tracing `Source → Middleware/Guard/Validator → Sink` to actively try to refute the candidate. Candidates that survive disproof require a concrete exploit scenario (`given <attacker/role/state> → when <action> → then <impact>`), confidence (`CONFIRMED` or `PLAUSIBLE` with named missing evidence), and unified severity (`BLOCKER` / `MAJOR` / `MINOR`). Disproved candidates are logged briefly as `REJECTED` (citing the protecting guard). | Eliminates hallucinated call graphs and false-positive warnings while proving every real finding end-to-end. | `03` |
| `SR12` | **Deterministic Security Sign-Off Verdict**:<br>• Any `CONFIRMED BLOCKER` or `CONFIRMED MAJOR` → `CHANGES_REQUESTED`<br>• Any `PLAUSIBLE BLOCKER` or `PLAUSIBLE MAJOR` (or any `UNCOVERED` unit in the Coverage Ledger) → `BLOCKED` (until confirming/disproving evidence is provided)<br>• `MINOR` findings only → `APPROVED` (with findings listed)<br>• Zero findings & `100% COVERED` ledger → `APPROVED` | Prevents ambiguous security sign-offs and enforces a clear bar for delivery. | `03` |
| `SR13` | **Safe Verification Boundary & Redacted Reporting**: Never exploit shared or production environments and never include live secrets or real PII in security reports; verify using local/disposable test harnesses or read-only code tracing. | A security review must never create a live security incident or credential leak. | `01`, `03` |
| `SR14` | **QA/QC Runtime Hand-Off & Prevention Feedback Loop**: Hand over `Role × Scope` permission scenarios and any runtime-dependent `PLAUSIBLE` checks to QA/QC (`quality-planning` / `quality-acceptance`) for live runtime verification; promote recurring vulnerability classes into `.agents/skills/secure-coding-standards/`. | Connects white-box code auditing with black-box QA runtime verification and hardens authoring rules over time. | `01`, `03` |
