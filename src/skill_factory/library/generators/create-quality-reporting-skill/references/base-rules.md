# Base Rules — Quality Reporting (`RP1`–`RP12`, Mandatory Compliance)

All rules below (`RP1`–`RP12`) are **mandatory compliance** across every generated `quality-reporting` skill. Each rule is written into the generated skill with the workspace's real report locations, vocabulary, and IDs alongside its rationale.

| # | Rule | Why | Target Reference |
|---|---|---|---|
| `RP1` | **Revision-Bound with Environment Record.** Every report names the tested revision (`commit SHA`), the approved test plan version, the review status/link, and the exact environment record (services, versions, seed/data state, stubbed dependencies, test accounts by role). | A test result without its revision and environment cannot be trusted or reproduced. | `01` |
| `RP2` | **Per-Case Results with Evidence Links.** One row per executed or planned case: Case ID, AC ID, verification surface/level, result (`PASS` / `FAIL` / `BLOCKED` / `NOT_RUN`), evidence artifact link, and linked defect ID (when `FAIL`). | Readers must be able to verify any line item without re-running the test suite. | `01` |
| `RP3` | **AC Coverage Derived Deterministically from Cases.** An AC is `PASS` only if all of its mapped cases are `PASS`; any `FAIL` → `FAIL`; no `FAIL` and any `BLOCKED` → `BLOCKED`; no `FAIL`/`BLOCKED` and any `NOT_RUN` → `NOT_RUN`. | Claiming AC coverage at the feature level hides individual failing or unverified criteria. | `01` |
| `RP4` | **Deterministic Feature Verdict by Criteria.** `ACCEPTED` requires every AC to be `PASS` and `0` open `BLOCKER` or `MAJOR` defects (`shared_contracts/flags_and_statuses.md`); `CHANGES_REQUESTED` when any AC is `FAIL` or any `BLOCKER`/`MAJOR` defect remains open; `BLOCKED` when required evidence could not be produced (`BLOCKED` / `NOT_RUN` / `UNVERIFIED`). | Explicit criteria make the feature verdict reproducible and non-negotiable. | `01`, `SKILL` |
| `RP5` | **Defects Tracked with Unified Severity & Lifecycle.** Every defect records ID, unified 3-tier severity (`BLOCKER` / `MAJOR` / `MINOR`), failing Case ID, lifecycle status (`open` / `fixed-awaiting-retest` / `verified` / `wont-fix` with explicit user decision), one-line summary, and reproduction link. | Untracked or ungraded defects silently ship to production. | `02` |
| `RP6` | **Explicit Limitations Header.** Stubbed external providers, cases not run and why, environments or roles not covered, and known flaky checks must be stated in the top summary block. | A clean-looking report with hidden coverage gaps is more dangerous than an honest partial report. | `01` |
| `RP7` | **Honest Counting.** `NOT_RUN`, `BLOCKED`, and `UNVERIFIED` never count as `PASS`; never round up ("almost all passed"); always show exact counts per status and the total denominator (`of <total> cases`). | Counting shortcuts are where test reports most often mislead stakeholders. | `01`, `SKILL` |
| `RP8` | **Evidence Hygiene & Redaction.** Never include secrets, credentials, tokens, or personal data (PII) in screenshots, HAR/network logs, or response bodies (redact before saving); store all evidence files inside the workspace's authorized artifact directory. | Test reports and evidence folders are shared more widely than isolated test environments. | `03` |
| `RP9` | **Authorized Destination & Distribution.** Write the report to the workspace's canonical report path and results ledger; never post reports or evidence to external channels (issue trackers, chat, email) without explicit user authorization for that post. | Acceptance reports contain internal architecture and defect details that require controlled distribution. | `03` |
| `RP10` | **Multi-Round Re-Test History.** Record every test round with its revision SHA, the exact cases rerun, and the round verdict; earlier failures remain visible in the history table after a later fix passes. | A complete re-test ledger proves whether fixes held and prevents regression amnesia. | `02` |
| `RP11` | **Verdict-First Executive Summary.** Place the feature verdict, one-line reason, case counts with denominator, AC coverage summary, open `BLOCKER`/`MAJOR`/`MINOR` defect counts, and limitations at the very top of the report before detailed tables. | Decision-makers read the top block first and need immediate clarity on release readiness. | `01` |
| `RP12` | **Immutable Expected Results.** Never edit or soften a test case's expected result inside the report to turn a `FAIL` into a `PASS`; record any approved departure from the test plan explicitly under `Deviations from the Plan`. | Moving the goalposts inside the report hides real defects and invalidates spec traceability. | `01` |
