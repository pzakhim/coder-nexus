# Base Rules — Implementation Planning (`IP1`–`IP17`)

All rules `IP1`–`IP17` below are **mandatory compliance** across every generated `implementation-planning` skill. Each rule is instantiated with the workspace's real module layout, commands, tools, and rationale. The fixed `implementation-planning` process rules (vertical behavior phases, mandatory `PHASE-00`, `AC-NN` coverage, single `code_writer` executing tasks in order, and `validate_plan_slices` passing with `PASS`) always apply.

| ID | Rule | Why | Target Reference |
|---|---|---|---|
| `IP1` | **Layer Order Inside One Vertical Behavior.** Define the repository's concrete layer order inside a single vertical behavior slice (e.g., contract/schema → domain → data/adapter → presentation/handler → wiring); phases remain vertical behavior slices. | Ensures downstream layers never stall mid-phase waiting for unbuilt upstream contracts or domain models. | `01` |
| `IP2` | **Single-Writer Ordered Task Shape.** One task = one explicit file scope + exact produced artifacts/signatures + one executable check command, ordered for a single `code_writer` running sequentially. | Gives `code_writer` and `code_reviewer` an unambiguous, self-contained unit of work. | `02` |
| `IP3` | **Architecture-Aligned File Paths.** Every file path in a task follows the workspace's `clean-architecture` skill; a plan never invents ad-hoc directories or layer bypasses. | Keeps implementation plans structurally consistent with workspace architecture boundaries. | `02` |
| `IP4` | **Real Targeted Check Command per Task.** Every task specifies the exact analyzer, linter, type-checker, or targeted test command with its working directory (`cwd`) that must exit `0` (`PASS`). | A check that cannot be executed deterministically proves nothing. | `02` |
| `IP5` | **Workspace `PHASE-00` Readiness Items.** Environments, test accounts per role, seed data, mock servers, migrations, and feature flags are enumerated in `PHASE-00`, each tagged `[EXECUTE]` or `[INFO_NOTE]` with a `PASS` / `FAIL` verification check. | Prevents `code_writer` from stalling mid-phase due to missing environment prerequisites. | `03` |
| `IP6` | **Definition of Done (DoD) per Phase.** Every phase ends only when all task checks report `PASS`, static analysis is clean, tests cover agreed pass/fail cases, migrations are verified on a disposable database (when applicable), and phase documentation is updated. | Gives `code_writer`, `code_reviewer`, and `test_runner` one shared finish line per phase. | `03` |
| `IP7` | **Branch, Sub-Ticket / Accepted-Phase Commit Checkpoints & Hotfix Tasks (`G2`, `G3`, `M3`, `M10`).** Branch, base, and merge targets come from the `git-preflight` / `git-workflow` `D-NN` decision record. Work branches are named after the **parent/umbrella ticket** (`<type>/<PARENT-TICKET>-<short-description>`, or `<type>/<short-description>` only when no tracker ticket exists). Each phase or sub-ticket boundary in the plan maps to an explicit verified commit checkpoint carrying the **sub-ticket ID** (`<type>(<SUB-TICKET>): <summary> [parent: <PARENT-TICKET>, PHASE-NN]`) or the **accepted phase ID** (`<type>(<PARENT-TICKET>): [PHASE-NN] <summary>` or `<type>(phase-NN): <summary>`) — never arbitrary WIP commits. Production hotfix plans include explicit propagation tasks for every active line (`release/*`, `develop`); merges into production (`main`) and release tags are listed only as commands for the user to run (`M6`). | Aligns plan checkpoints directly with `git-workflow` traceability and human accountability gates. | `01`, `03` |
| `IP8` | **Out-of-Workspace Work Is a Handoff or `BLOCKED`.** Changes in another repository, external infrastructure, or another team's service are recorded as explicit handoffs or `BLOCKED` dependencies in `PHASE-00`, never as `code_writer` tasks. | Agents must not plan edits outside the authorized workspace boundary. | `03` |
| `IP9` | **Unknowns Settled Early.** Technical uncertainties are resolved in `PHASE-00` or `PHASE-01` via a bounded probe or verification check, never deferred to final phases. | Surfaces architectural and integration risks while plan adjustments are cheap. | `01`, `03` |
| `IP10` | **Global Constraints Header.** Exact item-wide values pinned by approved `requirements.md` / `design.md` (limits, version floors, formats, fixed copy, naming, platform targets) are copied once verbatim with their source ID (`BR-NN`, `D-NN`, design section) into `## Global constraints` above `## AC coverage` in `implementation-plan.md`. Every task inherits them without paraphrasing. Any unpinned value becomes an open `Q-NN` before Gate 3, never an invented default. | Ensures `code_writer` enforces exact specification constants across every task. | `01` |
| `IP11` | **Review Focus Header.** Up to five uncovered input classes or failure modes implied by the spec (empty/oversized payloads, duplicate submit, concurrent edit, network drop, permission denial), ordered by likelihood, are listed in `## Review focus` above `## AC coverage` in `implementation-plan.md`. Each entry names the input, the expected behavior from the spec or `D-NN`, and the owning task that tests it (or `None found after checking every AC and BR` when complete). Unspecified expected behavior becomes a `Q-NN` before Gate 3. | Assigns an explicit task owner and test assertion to edge cases before coding starts. | `01`, `02` |
| `IP12` | **Repository-Derived Task Sizing (`XS`–`XL`) & Split Triggers.** Define `XS`, `S`, `M`, `L`, and `XL` from this repository's git history (reviewed commits that landed without rework). Split any task that is `XL`, touches 8+ files, contains `"and"` in its title, or crosses two independent subsystems. Split only at boundaries where a reviewer could reject one task and approve its neighbor; fold config, setup, and docs into the task whose behavior requires them. | Keeps tasks reviewable in a single pass without creating non-functional micro-fragments. | `02` |
| `IP13` | **High-Risk Vertical Behavior First (Extends `IP9`).** Immediately after `PHASE-00`, order the vertical behavior with the highest technical or domain risk first among phases permitted by dependencies. | Validates the riskiest assumptions before low-risk boilerplate is written. | `01` |
| `IP14` | **Prefactor First.** When a behavior-preserving refactor simplifies a planned feature change, schedule it as the first task of that phase inside approved scope, verified by existing tests passing (`PASS`), without mixing in new behavior. | Separates structural preparation from behavior changes so each diff is easy to verify. | `01`, `02` |
| `IP15` | **Expand → Migrate → Contract for Wide Renames.** Mechanical changes with wide blast radius across call sites (renaming a shared symbol, retyping a schema field) use three ordered steps: an **expand** task adding the new contract alongside the old, bounded **migrate** batch tasks per module/package, and a **contract** task removing the old form after all callers migrate. Every task keeps its check `PASS`. Schema changes follow `database-migrations`. | Prevents broken intermediate builds and keeps each migration batch independently revertible. | `01`, `02` |
| `IP16` | **Signatures and Pinned Values, Never Function Bodies.** Tasks specify file paths, exact signatures (name, parameters, return type), pinned spec constants, and test names with assertions — never transcribed function bodies (unless an exact algorithm or literal copy is mandated by the spec). | Carries architectural and contract decisions without bloating the plan into unverified code transcripts. | `02` |
| `IP17` | **Tests and Docs Inside Each Behavior Phase.** Every phase includes the unit/integration tests and documentation updates for its vertical behavior slice; never create a standalone final testing, documentation, or polish phase. | Guarantees every completed phase is self-contained, tested, and releasable (`IP6`). | `01`, `03` |
