# Base rules (generic, every workspace)

Each rule goes into the generated skill with the workspace's real sources, terms and examples **and its reason**, or is marked "not adopted" with a reason. The fixed `grilling` laws (draft first, confirm every inference, 0 open questions, one question at a time) always apply; these rules add content inside them.

| # | Rule | Why | Goes into |
|---|---|---|---|
| RS1 | **Source map.** Each kind of requirement: where it comes from, how it is read, which sources are often unreachable, which wins on conflict. Feeds the source inventory and sufficiency check of `goal-framing`. | The Source Inventory is right from the first turn. | 01 |
| RS2 | **Question bank per dimension.** For each `grilling` dimension (scope and data source, happy path and states, inferences, negative and edge cases, lifecycle), the questions this workspace usually needs, in its terms; each asked question names the `G-NN` it serves. | Fewer, better questions. | 02 |
| RS3 | **Mandatory edge cases.** The catalog categories the workspace really has, each with a real example; the Spec Writer checks each one against the item. | Defects cluster in familiar edge cases. | 03 |
| RS4 | **Observable AC, no vague words, measurable success.** Given/When/Then (or the team's format), one behavior per AC, no implementation words, testable by QA; examples from approved specs. A list of vague words the team must not write (for example "fast", "easy", "user-friendly", "gracefully", "as appropriate"), each with what replaces it: a number, a state, or an observable result. A vague word the user cannot pin down becomes a `Q-NN`, never a guess. Each goal's success signal names who observes what, and the threshold or event that proves it. | QA can test it, the user can read it; a vague word or an unmeasurable goal hides a decision nobody made. | 04 |
| RS5 | **Glossary terms verbatim.** Goals, BR, AC and scenarios use the glossary terms of `domain-knowledge` exactly; a synonym (including one listed under "Avoid saying") is a defect that `gate-review` reports. A new term is added to `domain-knowledge` first, or marked `OPEN` there and asked. | One name per thing across spec and code; two names make readers think there are two things. | 04, SKILL |
| RS6 | **Gate 1 review questions.** The workspace part of `gate-review` spec mode: questions about the spec text (not about the product), per job type, each tagged `[Gap]`, `[Ambiguity]` or `[Conflict]` and citing the section or ID it checks. They run after the validators and the fixed spec-mode checklist; each finding becomes a `Q-NN`. No separate ready checklist. | One review path for Gate 1; questions about the text find what checkboxes let pass. | 05 |
| RS7 | **Bug specs.** Reproduction steps, where it was found (DEV / STG / PROD), expected vs actual, affected users and data, regression scope. | A bug spec needs different facts than a feature. | 04, 05 |
| RS8 | **Language.** User-facing documents in the team's language; code names stay as in code. | The user approves what they can read. | SKILL |
| RS9 | **Fixed process unchanged.** No gate, `grilling` law, template section or validator rule is removed or renamed. | Workspace skills add content, not a different process. | SKILL |
| RS10 | **Delta for change jobs.** For a change (a feature or refactor delivered as a new `vN` of built behavior), each affected BR and AC is classified ADDED, MODIFIED or REMOVED against the built code at the baseline revision, with a one-line reason; a REMOVED item also carries a migration note (what happens to existing data, users or clients). The delta is written in `change-impact.md`: BR, workflow, endpoint and screen changes in "Behavior delta" (ADDED / MODIFIED / REMOVED, reason and effect on existing data and users); AC changes in "AC delta" with the values its column accepts (Add / Change / Remove, unaffected = Keep), each tracing to a behavior row. `requirements.md` of `vN` holds the full current set: MODIFIED items in their full new wording, REMOVED items absent. | Reviewers see exactly what differs; a wrong kind (new behavior marked MODIFIED) leaves nothing to compare. | 04 |

**Never "not adopted":** RS5, RS9, RS10.

## Job types

Gate 1 questions (RS6) and the delta (RS10) follow the work-item Types: feature, bugfix, refactor, optimization, migration, maintenance, investigation, documentation. "Change" is a feature or refactor delivered as a new `vN` with `change-impact.md`; "verification" is an investigation that produces `verification.md` findings only, no code. List only the Types the workspace uses.
