# Mandatory Base Rules (`V1`–`V12` — Visual Quality)

All 12 visual quality rules are **mandatory compliance** across every generated `visual-quality` skill. Each rule is mapped into `SKILL.md` and the 3 cohesive reference files (`01`–`03`) using the workspace's concrete design paths, UI tokens, components, and capture tools.

| ID | Mandatory Rule | Why | Placement |
|---|---|---|---|
| **V1** | **Compare against an approved reference** — Use the extracted Figma per-screen `.png` renders, `<stem>.spec.json`, and `design.md` (`## UI/UX mapping`) at the approved revision; use the pre-change UI as a labeled baseline only when the approved plan explicitly allows it. | Without a fixed reference, "looks right" is subjective opinion. | `SKILL`, `01` |
| **V2** | **Like-for-like matrix (`Screen × State × Viewport × Theme`)** — Capture every screen across all 4 required visual states (`Loading`, `Content`, `Empty`, `Error`) at the confirmed viewport, orientation, role, and theme. | Different inputs or viewports produce false diffs or hide state-specific layout bugs. | `SKILL`, `01` |
| **V3** | **Real runtime or headless target capture** — Render the UI on the workspace's real target (simulator, emulator, desktop, browser, or approved headless golden harness) and save screenshots under the revision-bound evidence path. | Static code analysis or Cubit/state unit tests never prove rendered layout or overflow freedom. | `01`, `02` |
| **V4** | **Inspect real images (a file path alone is `UNVERIFIED`)** — Open and visually inspect every captured `.png` screenshot before claiming `PASS`. | A saved screenshot file can contain a blank screen, crash overlay, or layout overflow. | `SKILL`, `01`, `02` |
| **V5** | **Preserve API & data provenance (`FE_MOCKOON` vs `BE_LIVE`)** — Record whether each screenshot was captured against contract-derived Mockoon fixtures (`FE_MOCKOON`) or live services (`BE_LIVE`). Fixture-backed screenshots prove UI/contract rendering only, never live backend integration. | Prevents mistaking mocked UI screenshots for end-to-end live acceptance. | `SKILL`, `01` |
| **V6** | **Judge by 10 named dimensions, never personal taste** — Evaluate Layout & Hierarchy, Spacing & Alignment, Typography, Color & Tokens, Shared Components, Icons, 4 UI States, Responsiveness & Safe Area, Copy, and Accessibility (`48x48dp` / `44x44pt` touch targets, `4.5:1` contrast). | Named dimensions turn subjective taste into verifiable engineering checks. | `03` |
| **V7** | **Grade deviations with `BLOCKER` / `MAJOR` / `MINOR`** — `BLOCKER`: layout overflow/clipping, missing required state, wrong component/token breaking hierarchy or contrast, broken responsiveness, or copy changing meaning (`FAIL`). `MAJOR`: edge-state visual defect or noticeable spacing/alignment drift (`FAIL`). `MINOR`: cosmetic nuance that does not affect usability or design-system compliance. Deviations explicitly authorized by `D-NN` are `ACCEPTED (D-NN)`. | Aligns visual review with `shared_contracts/flags_and_statuses.md` §2. | `SKILL`, `03` |
| **V8** | **Strict Golden & Baseline Governance** — Baseline creation/update runs only during implementation (`Code Writer`) and requires human/Reviewer visual inspection (`Code Reviewer`). Pre-release verification (`Test Runner`) never runs baseline-overwrite flags (e.g. `--update-goldens`). | Overwriting golden baselines during verification masks visual regressions as passes. | `SKILL`, `02` |
| **V9** | **Per-screen & per-state evidence table** — Record each `Screen / State / Viewport` row with its reference, screenshot path, deviation severity, and canonical status (`PASS` / `FAIL` / `BLOCKED` / `NOT_RUN` / `UNVERIFIED`, or `N/A` when `UI Impact: No`). | Makes every visual verdict traceable to an exact image and revision. | `03` |
| **V10** | **Missing reference, target, or state is never `PASS`** — Missing visual reference or unavailable target device/emulator is `BLOCKED`; an uncaptured required state is `NOT_RUN`. | Absence of visual evidence is not visual fidelity. | `SKILL`, `01`, `03` |
| **V11** | **Zero secrets or personal data in screenshots** — Use safe test/fixture data only and redact any credentials or PII before saving artifacts. | Screenshots are shared broadly in reports and PRs. | `SKILL`, `01` |
| **V12** | **Read-only inspection during Review & Verification** — Never patch UI code, styles, or golden baselines during Code Review or Test Runner verification; return `FAIL` → `CHANGES_REQUESTED`, and invalidate prior visual evidence whenever code changes. | Preserves independent verification and revision integrity. | `SKILL`, `03` |
