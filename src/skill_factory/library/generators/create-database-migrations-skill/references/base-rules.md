# Base Rules — Database Migrations (Mandatory Compliance)

Every generated `database-migrations` skill must enforce all 14 base rules (**M1–M14**) adapted to the workspace's migration runner, database engine, and environment topology:

| # | Rule | Why It Is Mandatory | Target Reference |
|---|---|---|---|
| **M1** | **Use the real migration runner; verify target identity first.** Inspect the runner's config (`alembic.ini`, `env.py`, etc.) and verify the target DB host/name (without printing secrets) before running any command. | Running the wrong runner or hitting the wrong database is the most destructive mistake possible. | `01` |
| **M2** | **Enforce 3-Tier Environment Authority (`Local/Disposable` vs `Develop` vs `Staging/Production`).** (1) **Local / Disposable DB**: agent runs autonomously for verification; (2) **Develop (`develop`)**: agent may run migrations **only when the user explicitly requests/approves it in the session** (never autonomously); (3) **Staging & Production (`staging`, `production`)**: **never executed by the agent** — always handed off to DevOps via the Migration Handoff Packet. | Having credentials in `.env` never grants authority to mutate shared or production environments without explicit governance. | `01`, `03` |
| **M3** | **Never deliver schema changes via reset, sync, seed, or `create_all` tools.** Schema DDL and tracked data migrations ship exclusively through versioned revision files. | Reset/sync commands bypass history, drift environments, and destroy business data. | `01`, `SKILL` |
| **M4** | **Roll out breaking changes via `Expand → Backfill → Contract`.** Add backward-compatible structure first, deploy dual-read/write code, backfill data, switch code, and contract/drop in a later phase. | Old and new application/worker instances run concurrently during deployments. | `02` |
| **M5** | **Immutable, self-contained, linear revisions.** Never edit a revision already applied to `develop`, `staging`, or `production` (add a new revision instead); keep a single linear head (`down_revision`); never import live application models/services inside a revision. | Editing applied revisions splits environment history; importing live models breaks historical replays. | `01` |
| **M6** | **Respect existing rows when adding `NOT NULL` or constraints.** Use safe constant `server_default`s or add constraints as `NOT VALID` first, backfill/fix existing violations, then `VALIDATE CONSTRAINT`. | Adding a strict constraint over violating rows fails the deploy or locks the table. | `02` |
| **M7** | **Enforce lock timeouts and online DDL on populated tables.** Set `lock_timeout` at the start of `upgrade()`, estimate row counts, and build/drop indexes `CONCURRENTLY` outside a transaction block. | An unguarded `ACCESS EXCLUSIVE` or `SHARE` lock behind a slow query causes an immediate production outage. | `02` |
| **M8** | **Batched, resumable, scope-aware, parameterized data backfills.** Every data migration filters by the required tenant/organization/environment scope, runs in key-ordered batches (`WHERE col IS NULL`), uses bind parameters, and checks an invariant query (`= 0` remaining) afterward. | Unscoped or single-transaction updates corrupt cross-tenant data and hold long table locks. | `02` |
| **M9** | **Verify on a disposable database (`PASS` / `FAIL`).** Prove clean install (`upgrade head`), single head & zero model drift, upgrade over seeded multi-tenant data, backfill invariants, reversibility (`downgrade -1 && upgrade head`), valid indexes, and automated migration tests before handoff. | Only executing against realistic data on a disposable DB proves the migration works both ways. | `03` |
| **M10** | **Define backup and recovery before applying to any shared target.** Document exact pre-migration backup commands and specify what `downgrade` restores vs. what requires a backup restore. | Rolling back application code never rolls back database mutations. | `03` |
| **M11** | **Track canonical migration states alongside core gate statuses.** Report `NOT_REQUIRED`, `PENDING`, `READY_FOR_HANDOFF`, `APPLIED_UNVERIFIED`, `VERIFIED_IN_TARGET`, or `FAILED` with command evidence. | Distinguishes local verification from actual target deployment state. | `03` |
| **M12** | **Always produce a complete DevOps Migration Handoff Packet (`migration-handoff.md`).** Every migration produces a secret-free handoff document containing: (1) **Summary of Changes & Why** (every schema/data change and its business/technical reason), and (2) **Step-by-Step Execution Runbook for DevOps across `develop`, `staging`, and `production`** (covering both schema DDL and data backfill commands, sequencing, pre-backups, and postchecks). | Enables the user and DevOps to audit why the DB is changing and execute `develop`, `staging`, and `production` migrations safely without Backend intervention. | `03` |
| **M13** | **Keep schema migrations separate from seed/demo data.** Never mix test fixtures or demo seeds into production schema revisions. | Couples infrastructure schema history to non-production data. | `01` |
| **M14** | **Zero secrets or PII leaks in revisions and handoffs.** Never embed connection strings, credentials, or customer PII in revision files, logs, or handoff packets. | Revisions and handoff packets are committed and shared across teams. | `02`, `03` |
