# Base Rules — Quality Acceptance (`A1`–`A14`, Mandatory Compliance)

All rules below (`A1`–`A14`) are **mandatory compliance** across every generated `quality-acceptance` skill (never dropped or skipped).

| ID | Rule | Why | Target Reference |
|---|---|---|---|
| `A1` | **Approved Plan, Reviewed Revision & Prepared Environment**: Execute acceptance tests only after code review (and security review when triggered) approved the exact target revision (`HEAD` SHA); run the approved test plan against the prepared environment (`quality-environment`). | Testing an unreviewed or mismatched revision proves nothing about what ships. | `01` |
| `A2` | **Strictly Read-Only Toward Code & Tests**: Never edit application source code, migrations, or automated test files during acceptance execution; report defects with reproduction steps back to the Code Writer. | A tester who modifies application code loses independence and invalidates the review gate. | `01`, `SKILL` |
| `A3` | **Execute Cases as Written**: Follow the approved steps, inputs, and expected results verbatim; record any deviation explicitly and never improvise or soften an expectation to force a pass. | Improvised steps or softened expectations hide regressions and prevent run-to-run comparison. | `01` |
| `A4` | **Real Data Paths & Persistence Read-Back**: Exercise real service and storage paths; verify every state mutation by reading back from persistence (reload the UI view or re-query the API/storage) rather than trusting optimistic UI state. | Optimistic UI state without persisted read-back creates false `PASS` outcomes. | `01`, `02` |
| `A5` | **UI / Client Surface Execution in a Real Runtime**: Produce all required UI states for real (`loading`, `empty`, `error`, `populated`), verify capability-driven visibility per role in isolated sessions, verify environment/scope switching, and inspect runtime console/log errors and network requests after every flow. | End users interact with the rendered client runtime, not static component trees or mocked unit harnesses. | `02` |
| `A6` | **API / Service Surface Execution & Security Hand-Off (`SR14`)**: Authenticate per role and execute against the real API/service entrypoint; verify status codes, response schemas, persisted state, idempotency, and asynchronous side effects (jobs, events, audit logs); execute live runtime verification of the **`Role × Environment × Action × Object` permission matrix** (direct unauthenticated `401`, forbidden `403`, and cross-tenant/cross-owner `403`/`404` anti-IDOR calls) plus any runtime-dependent **`PLAUSIBLE`** checks handed over by `security-review` (`SR14`). | Authorization, tenant isolation, and domain invariants are enforced at the service boundary regardless of what the UI hides. | `02` |
| `A7` | **No Tool Output, No Result (`BLOCKED`)**: If the configured UI/client or API/service verification tool is unreachable and its fallback also fails, mark affected cases `BLOCKED` with the exact tool error; never infer or describe results that were not observed from live tool output. | Unobserved results reported as passes are fabricated evidence. | `01`, `02` |
| `A8` | **Revision-Bound Evidence per Case**: Capture executed steps, observed outputs, screenshots or redacted API request/response payloads saved under the workspace's evidence path, runtime console/network excerpts, git revision SHA, environment record, and any explicitly stubbed external providers. | Revision-bound evidence makes every verification decision auditable and reproducible. | `01` |
| `A9` | **Unified Case Result Vocabulary (`PASS` / `FAIL` / `BLOCKED` / `NOT_RUN`)**: Grade every test case using strictly `PASS`, `FAIL`, `BLOCKED`, or `NOT_RUN` (`shared_contracts/flags_and_statuses.md`); `BLOCKED`, `NOT_RUN`, and `UNVERIFIED` never count as `PASS`. | A single deterministic vocabulary prevents ambiguous or inflated sign-off reports. | `01` |
| `A10` | **Actionable Defect Reports with Unified Severity (`BLOCKER` / `MAJOR` / `MINOR`)**: Every `FAIL` produces a structured defect entry citing the exact failing step, expected vs. actual behavior, saved evidence, minimal reproduction command/steps, suspected boundary, and unified severity (`BLOCKER` / `MAJOR` / `MINOR` per `shared_contracts/flags_and_statuses.md`). | Complete, severity-graded reproductions let the Code Writer fix defects in a single round. | `03` |
| `A11` | **Out-of-Scope Guard & Regression Execution**: Execute the plan's out-of-scope guard cases and regression suite alongside new feature cases on the same revision. | Regressions in adjacent workflows block release readiness just like primary feature failures. | `02` |
| `A12` | **Re-Test Protocol on the Fixed, Re-Reviewed Revision**: After a defect fix and re-review on the new revision SHA, re-execute all previously failed cases plus the regression cases covering the modified blast radius. | Fixes frequently introduce side effects in neighboring code paths. | `03` |
| `A13` | **Safe Execution Boundary & Redacted Evidence**: Use designated test accounts only; never mutate production or unapproved shared environments; never perform destructive actions outside the approved test plan; redact all secrets, tokens, and real PII from screenshots, payloads, and logs. | Acceptance testing must never cause a live operational or security incident. | `01` |
| `A14` | **Flakiness Classification & Deterministic CLI Gates (`PASS` / `FAIL`)**: Re-run an unexpected failure once to classify intermittency; report intermittent behavior as flaky (`FAIL` / `BLOCKER` or `MAJOR`, never `PASS`) with both run artifacts, and run deterministic CLI acceptance/smoke gates reporting strictly `PASS` or `FAIL`. | Masking flaky tests as passes ships non-deterministic defects into production. | `03` |
