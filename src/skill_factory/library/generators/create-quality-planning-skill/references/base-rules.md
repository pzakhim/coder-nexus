# Base Rules (`Q1`–`Q14` — Mandatory Compliance)

Generalised from Coder Nexus `plugins/core/agents/test_runner.md` and workspace verification contracts. Every rule **`Q1`–`Q14`** is **mandatory compliance** across every workspace (zero optional rule carve-outs) and goes into the generated skill with the workspace's real spec paths, IDs, roles, and its reason.

| # | Rule (Mandatory Compliance) | Why | Reference Target |
|---|---|---|---|
| `Q1` | **Specs are the source of truth.** Design cases from the brief (scope in/out), requirements (AC, BDD scenarios), design (state matrix, contracts), decisions (`D-NN`), and glossary — never from the implementation plan or source code. | Cases derived from the code only prove the code does what it already does. | `01-sources-testability-and-traceability.md` |
| `Q2` | **Review testability early.** Right after the requirements gate, flag any AC without an observable outcome, with vague words ("fast", "user-friendly", "works properly"), or missing input/scope definitions, and send questions back to the spec owner. | An untestable AC found early costs a question; found during test execution it blocks the release. | `01-sources-testability-and-traceability.md` |
| `Q3` | **Two-way traceability (`AC-NN ↔ TC-NN`).** Every AC and BDD scenario maps to at least one test case; every test case cites its AC or is explicitly marked `regression`, `out-of-scope-guard`, or `security-handoff` (`SR14`). | Uncovered AC leave blind spots; orphan tests hide unrequested behavior or wasted maintenance. | `01-sources-testability-and-traceability.md` |
| `Q4` | **Cover all risk categories + `security-review` (`SR14`) hand-off.** Cover happy paths, validation errors, `Role × Environment × Action × Object` permission matrix denials (including direct API/service `401`/`403`/`404` calls and runtime-dependent `PLAUSIBLE` items handed over from `security-review`), UI/client states (loading, empty, error + retry, populated), boundary values, external provider failures/timeouts, and idempotency/concurrency. | Most escaped defects and access-control bypasses live off the happy path or bypass the UI. | `02-case-design-and-test-levels.md` |
| `Q5` | **Cheapest proving test level.** Choose the lowest, fastest stack-neutral test level that proves the requirement: API/Service Acceptance for business rules, persistence, and permissions; UI/Client End-to-End for user journeys and state transitions; Visual Fidelity for approved layouts; Manual only with a written justification. Unit tests belong to the Code Writer. | Running every permutation through full UI End-to-End makes the suite slow, brittle, and unable to isolate root causes. | `02-case-design-and-test-levels.md` |
| `Q6` | **Safe, repeatable test data.** Seed data per case or per run from deterministic, non-production sources; clean up or isolate state; never copy production PII/secrets and never fabricate hardcoded "successful" fallback data when a dependency is missing (`BLOCKED`). | Shared mutable state or fabricated data produces false `PASS` verdicts. | `03-data-environments-and-plan-gates.md` |
| `Q7` | **Named environments and labelled stubs.** Specify which target environment each case group runs on; stub external third-party providers only at the network/adapter boundary where the plan authorizes it, and explicitly label stubbed runs in the test report. | A `PASS` against a stub does not prove live contract compatibility with the real external provider. | `03-data-environments-and-plan-gates.md` |
| `Q8` | **Unified `BLOCKER` / `MAJOR` / `MINOR` risk tiers.** Grade every test case by business and security impact using `BLOCKER` (critical flows, auth/scope isolation, data integrity), `MAJOR` (validation, state transitions, shared regressions), and `MINOR` (cosmetic, rare edge cases) (`shared_contracts/flags_and_statuses.md`). Execute `BLOCKER` cases first. | Unified severity tiers align test execution order directly with release-gate blockers. | `02-case-design-and-test-levels.md` |
| `Q9` | **Out-of-scope guards.** Include explicit guard cases proving items listed under "scope out" or forbidden transitions are not exposed or executable. | Unrequested features and unguarded endpoints introduce untested security and regression risk. | `02-case-design-and-test-levels.md` |
| `Q10` | **Targeted regression set.** Include cases for existing workflows touching shared modules, database tables, contracts, or permission guards modified by the feature. | Changes break neighboring consumers and shared contracts more often than the primary happy path. | `02-case-design-and-test-levels.md` |
| `Q11` | **Concrete, observable expected results.** State exact status codes, response payloads, persisted records, domain events, or rendered UI states/messages — never vague phrases like "works as expected" or "succeeds". | Vague expectations cannot deterministically fail, so they prove nothing. | `02-case-design-and-test-levels.md` |
| `Q12` | **Canonical ID scheme.** Use one consistent ID scheme for acceptance criteria (`AC-NN`), scenarios, and test cases (`TC-NN`) across the test plan, execution logs, and defect reports. | Shared identifiers make traceability automated and audit-ready across roles. | `01-sources-testability-and-traceability.md` |
| `Q13` | **Plan gate before execution.** Validate the test plan with deterministic CLI checks (`PASS` / `FAIL`) and review it against the `BLOCKER` / `MAJOR` / `MINOR` rubric before execution; whenever AC or specs change, update the plan first. | Executing an incomplete or outdated test plan wastes test runs and misses updated requirements. | `03-data-environments-and-plan-gates.md` |
| `Q14` | **Strict independence from implementation.** Inspect source code only to locate execution targets (routes, endpoints, selectors, seed commands), never to derive expected behavior; never weaken a test expectation to match buggy code. | The Quality Engineer validates the approved specification on behalf of the user, not the implementation as written. | `01-sources-testability-and-traceability.md`, `SKILL.md` |
