# Base rules (generic, every workspace)

Generalised from Coder Nexus bug-hunt base rules and the bug-hunt practice of a real fullstack workspace. Each rule goes into the generated skill with the workspace's facts (vocabulary, report location, commands) **and its reason**, or is marked "not adopted" with a reason.

| # | Rule | Why | Goes into |
|---|---|---|---|
| H1 | **One question:** with which input or state does this change produce a wrong result, a crash, a hang, a leak, a data-scope breach or a security hole? Compliance, style and complexity are out of scope. | Mixing compliance into the hunt drowns real defects in noise. | SKILL, 01 |
| H2 | **Fixed revision.** Record base and review revisions plus the staged, unstaged and untracked files of the item; review exactly that tree. | Findings must refer to code that will actually ship, not a moving target. | 01 |
| H3 | **Whole context and callers.** Read each changed hunk with its whole function/class; for each changed public symbol (signature, return type, nullability, raised errors, response shape, route, JSON key, hook return), find and read its callers. A broken caller outside the diff is in scope. | Most regressions show up in callers, not in the changed lines. | 01 |
| H4 | **Cold pass first.** Hunt from the code before reading requirements, design or plan; read them afterwards only to decide whether a suspicious behavior is intended. | Knowing the intent makes the reader see what the code should do instead of what it does. | 01 |
| H5 | **Seven dimensions.** Walk the scope once per dimension (`dimensions.md`) and write every suspicion down as `file:line — hypothesis`. | A systematic walk finds what an intuitive read skips. | 01 |
| H6 | **Disprove every candidate.** Trace the real path from an entry point (route, use case, job, screen action) to the line, reading guards, defaults and framework behavior; use read-only commands where they decide it. Never modify application code or tests during the hunt. | A candidate that survives an honest attempt to refute it is worth the reader's time. | 02 |
| H7 | **No scenario, no finding.** Every finding states `given <input/state> → when <action> → then <wrong result>` with concrete values. "Might be fragile" is not a finding. | Scenarios are reproducible and turn directly into tests. | 02 |
| H8 | **Verdict classes.** `CONFIRMED` (path traced end to end or a command demonstrated it), `PLAUSIBLE` (depends on something not visible — name what would confirm it), rejected (drop silently). | Readers must know how certain a finding is. | 02 |
| H9 | **Severity.** `BLOCKER` (data loss/corruption, scope breach, authorization bypass, crash/hang on a normal path, approved behavior broken), `MAJOR` (wrong result/crash on a realistic edge path, resource leak), `MINOR` (rare or self-correcting) — mapped to the workspace's finding levels. | One scale for coder and reviewer avoids negotiation. | 03 |
| H10 | **Effort follows the item.** `quick` (self-check, small item: dimensions 1–4 on changed hunks, cap 5), `standard` (every phase review: 1–7, cap 10), `deep` (risky code or a phase returned twice: 1–7 + callers one level further, no cap). Workspace lists its deep triggers. | Effort matched to risk keeps reviews fast where they can be and thorough where they must be. | 03 |
| H11 | **Report format.** One row per finding (ID, severity, verdict, file:line, defect, scenario, evidence, fix direction), most severe and CONFIRMED first; end with a summary line naming effort and dimensions covered. | A fixed format is easy to act on and to compare across rounds. | 03 |
| H12 | **Verdict impact.** CONFIRMED BLOCKER/MAJOR blocks; PLAUSIBLE BLOCKER blocks until the named evidence arrives; other PLAUSIBLE go to the writer as questions; MINOR does not block alone. The same finding returned a third time escalates instead of looping. | Clear consequences stop endless review rounds. | 04 |
| H13 | **Roles.** Reviewer: standard/deep, read-only, writes findings to the report. Code Writer: quick self-check after targeted checks pass, fixes CONFIRMED findings inside the approved scope **with the missing test**, lists open PLAUSIBLE in the handoff; a fix that changes behavior/API/design goes back to planning. | The writer catches cheap bugs early; the reviewer stays independent. | 04 |
| H14 | **Cleanups are notes.** Reuse/simplification/efficiency without a failure are listed as `NOTE` for code-simplification and never block. | Keeps the defect list about defects. | 03 |

**Never "not adopted":** H1, H2, H6, H7, H8, H13.
