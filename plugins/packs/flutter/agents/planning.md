## Flutter rules

- **FE Data Pipeline**: `RemoteDataSource` calling `ApiService` / HTTP client, `Model.fromJson`, `RepoImpl`, `UseCase`, and DI.
- **UI & Design System**: `planning` performs **Codebase & UI Kit class mapping** via `{{slot:architecture-design}}` (and its active profile contract for `imespro` / `external-structured` / `external-standard`), maps each UI need to exact widget/class names, records any `Core gap`, and specifies `BaseScreen`, `Router`, and `Cubit State` contracts.
- **Flutter Client**: resolve the `architecture_profile.mode` with `{{slot:architecture-design}}` **first**; the selection rules and each profile's planning duties live in `{{slot:architecture-design}}` (`references/01-context-scan-and-decisions.md` and the injected profile contract).
- **Step 1A scans**: Execute the 6 Codebase Intelligence scans following `{{slot:architecture-design}}` (`pubspec.yaml`, workspace foundations, Router, DI, module code, `get_ux_error_patterns`).
- **`design.md` specifics**:
  1. **Architectural Decision & Profile**: Record the locked-in `architecture_profile` (`mode`, `core_source`, evidence paths, rationale).
  2. **Target Directory Tree**: reduce `get_project_structure` to the folders this feature actually needs under `lib/modules/<feature>/`.
  3. **Screen, Routing & DI Contract**: Specify screen base inheritance (`BaseScreen` in `imespro`, client base in `external-structured`, or standard widget in `external-standard`).
  4. **State Management & Data Flow**: Define Cubit states, Cubit methods, and only the UseCases and Repositories the behavior needs.
  5. **Mockoon design**: follow `{{slot:architecture-design}}` reference `references/02-screen-state-api-and-ui.md`.
  6. **Core Usage table**: `Core usage` table for `imespro`, `Client Core Mapping` for `external-structured`, or UI specification for `external-standard`.
  7. **UI/UX mapping** (when `requirements.md` has non-`EXISTING` `S-NN` screens or `NEW` / `CHANGED` UI): audit `.superpowers/sources/<ISSUE-ID>/figma/tokens.json`, `<stem>.spec.json`, and `<stem>-SNN.png` (or codebase tokens when `CODEBASE_ONLY`) via `{{slot:ui-kit-mapping}}` (`references/03-widget-mapping-and-design-handoff.md` and the active profile contract); map each `S-NN` → screen class, route and arguments; map each token/node → widget; and map each new/custom component (`C-NN`) → widget under `lib/modules/<feature>/presentation/widgets/` (or the shared folder when two modules need it) with an explicit `Core gap` note surfaced to the user at Gate 2 when the active UI kit has no fitting widget.
- **Task acceptance checks**: `flutter analyze` or a targeted unit test.
- **Review DoD**: developer unit tests (UseCases, Mappers, Cubit emissions covering the agreed Pass/Default and Fail data) and zero-error `flutter analyze` requirements for Code Reviewer.
- **Gate 3 Flutter `test-plan.md` (`E2E-01..E2E-N`) & `final_qa` L3 Escalation**:
  - Author `.superpowers/work-items/<slug>/vN/test-plan.md` defining sequential `E2E-01..E2E-N` scenarios for `test_runner` across the **Flutter Verification Ladder**: (1) `flutter analyze` & widget/UI integration suites (`flutter test`), (2) runtime app execution & multi-screen workflow (`W-NN`) navigation, (3) all 4 Visual States (`Loading`, `Content`, `Empty`, `Error`), (4) Golden Screenshot (without `--update-goldens`) / extracted Figma `<stem>-SNN.png` visual comparison (`{{slot:visual-quality}}`), and (5) profile-specific invariants (under `imespro`: `BaseScreen` route observer & responsive hooks, `ListViewPaging` auto-load & pull-to-refresh, and `app_ui_kit` widget interactions).
  - When `bug_fixer` raises an `L3` `PCR-NN.md` during `final_qa` (e.g., an unrecorded `Core gap` in `../app-core` / `../app-util` / `../app-ui-kit`, a `BaseScreen` or `lib/core/` / `lib/shared/` boundary change, or a Router/DI/Cubit state-matrix design flaw), resolve it via `change-control` before `test_runner` re-verifies `E2E-01..E2E-N` from start to finish.
