## Flutter rules

### Flutter Architecture & Screen Rules
Apply the active `architecture_profile.mode` recorded in `design.md` (and `.superpowers/setup.json`) using the profile contracts in `{{slot:clean-architecture}}`, `{{slot:clean-code}}`, and `{{slot:ui-kit-mapping}}`:

- **`imespro`**: `coder-nexus setup flutter --check` must be `READY`. Read the relevant `../app-*/guidance/GUIDE.md` sections, `examples/`, and `lib/*.dart` signatures. Use exactly the core APIs the `Core usage` table marks as reused and build in the Client only what it records as a gap; never edit, format, or copy files in `../app-*`. Route screens live in `presentation/screens/*_screen.dart`. Use a UI Kit widget (`AppButton`, `AppFormField`, `AppDialog`, `AppLoadingIndicator`, `AppNoData`, `ListViewPaging`) when its GUIDE "Use when" fits the approved need; never substitute a raw Material button or input where a fitting UI Kit widget exists.
- **`external-structured`**: Read the Client's base files in `lib/core/` and `lib/shared/` per the `Client Core Mapping` table and follow the existing feature layout recorded in `design.md`.
- **`external-standard`**: Keep feature code together and create only the Domain/Data/Presentation responsibilities actually needed, with no empty layers or mandatory Cubit/DI dependencies. Standard Flutter widgets are correct.

- **Data layer**: In the Flutter Client (`lib/`), implement only the real **`RemoteDataSource`** calling `ApiService` (`ApiConfig.domain` pointed to the BE server or local Mockoon server in `.env`); **never** create fake `Mock<Feature>DataSource` classes inside `lib/`. When BE delivers the real API, point `ApiConfig.domain` / `.env` to the live server.
- **Unit tests & Optional Local `integration_test/` (Hybrid E2E)**:
  - For every domain usecase, data model/mapper, remote data source, and cubit state machine in `PHASE-01+`, create unit test files under `test/modules/<feature>/..._test.dart`.
  - When scheduled in the Gate 3 approved phase plan, author `integration_test/<feature>_e2e_test.dart` (`{{slot:unit-testing}}`) and verify it passes (`flutter test integration_test/<feature>_e2e_test.dart`).
- **4-State Visual Capture & `Visual Artifacts:` (`{{slot:visual-quality}}`)**: On every UI phase end and mid-phase `[REVIEW_CHECKPOINT]`, capture revision-bound 4-state `.png`s (`Loading`, `Content`, `Empty`, `Error` — via headless `golden_screenshot --update-goldens` when configured, or simulator/Chrome capture) into `vN/evidence/<phase-id>/<REVIEW_REVISION>/visual/`, self-check via parallel multimodal `read_file` against Figma (`figma/<stem>-SNN.png`) or HTML sitemap (`sitemap/screens/*.png`), and list every captured `.png` path in `writer-handoff.md` under **`Visual Artifacts:`**.
- **Local Self-Verification**: For `PHASE-01+`, run `dart format`, `flutter analyze`, `dart run dart_code_linter:metrics analyze lib` *(when configured)*, `flutter test test/modules/<feature>/`, and invoke `validate_architecture_code` / `validate_module_architecture` MCP tools with the approved `architecture_profile`.
