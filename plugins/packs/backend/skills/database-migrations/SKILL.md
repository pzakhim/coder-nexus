# Database migrations (Alembic + PostgreSQL)

Stack knowledge only. Planning of expand → migrate → contract across phases is core (`implementation-planning`); task loop, evidence rows and statuses are core (`incremental-implementation`, `work-item-contract`, `evidence-standard`). Model and index design is [postgres](../postgres/SKILL.md); where `alembic/` lives is `{{slot:clean-architecture}}`; personal data moved by a migration follows `{{slot:secure-coding-standards}}`.

## Never

| Never | Reason |
|---|---|
| Apply a migration to a shared environment (dev server, staging, production) yourself. The agent runs Alembic only against a local or disposable database. | Having credentials is not authority; shared databases are owned by the user / DevOps, who apply from a handoff packet ([05](references/05-applying-states-and-handoff.md)). |
| Change schema any other way: `Base.metadata.create_all()` outside tests, hand-written DDL in `psql`, the postgres MCP server, editing the `alembic_version` table, `alembic stamp` to skip a revision. | Changes outside the revision chain drift between environments and cannot be reviewed, repeated or rolled back. |
| Edit or delete a revision that has been applied to any shared environment. Add a new revision instead. | Environments that already ran it will never run the edit; history diverges. |
| Ship an autogenerated revision without reading and correcting it. | Autogenerate misses renames (drop + add = data loss), anonymous constraints, server defaults, and knows nothing about locks or existing rows. |
| Put expand and contract in one revision, or drop/rename something the running version still reads. | Old and new code run side by side during a deploy. |
| Weaken a test, delete a failing migration test, or mark `upgrade`/`downgrade` checks `PASS` without running them. | `NOT_RUN` is not `PASS` (core). |
| Write a secret (connection string, password) into a revision, a command, evidence or the handoff. | Revisions are committed; handoffs travel. Refer to "`DATABASE_URL` from `.env`". |

## The path for one schema change

1. **Know the setup** — read `alembic.ini`, `alembic/env.py`, the newest revisions and how the URL is loaded; detect the command prefix (`uv run`, `poetry run`, or the activated venv). Record facts in `codebase-notes.md`. → [01](references/01-alembic-workflow.md)
2. **Design** — classify the change (additive / needs backfill / destructive), choose the safe pattern, estimate rows and lock level, split into expand / backfill / contract as the plan's phases say. → [02](references/02-safe-schema-changes.md), [03](references/03-data-backfills.md)
3. **Generate and hand-edit** — `alembic revision --autogenerate -m "<imperative summary>"`, then review every operation, fix renames, add `lock_timeout`, `CONCURRENTLY`, `NOT VALID`, a real `downgrade()`. → [01](references/01-alembic-workflow.md)
4. **Verify on a disposable database** — `alembic upgrade head` from empty, upgrade from the previous head **with data**, `alembic downgrade -1`, `alembic upgrade head` again, `alembic check`, invalid-index query, affected tests. → [04](references/04-verification.md)
5. **Record the migration state and hand off** — evidence rows per command; state `PENDING` / `READY_FOR_HANDOFF`; the packet for whoever applies it to shared environments. → [05](references/05-applying-states-and-handoff.md), [template](templates/migration-handoff.md.tpl)

## Task checks (examples for the plan)

Commands come from the workspace (detected in step 1), run from the backend root, against the disposable database named in `PHASE-00`:

| Check | Command (cwd: backend root) | Expected |
|---|---|---|
| Revision applies | `uv run alembic upgrade head` | exit 0, `Running upgrade <prev> -> <new>` |
| Reversible | `uv run alembic downgrade -1 && uv run alembic upgrade head` | exit 0 both ways |
| Models and migrations agree | `uv run alembic check` | `No new upgrade operations detected.` |
| One head | `uv run alembic heads` | exactly one line |
| Behaviour on the new schema | `uv run pytest tests/<area> -q` | named tests pass |

Replace `uv run` with `poetry run` or nothing per the workspace. A check that could not reach the disposable database is `BLOCKED`, never skipped.

## Migration states

Recorded in the evidence and the hand-off as a field beside the core status; they never replace a core status.

`NOT_REQUIRED` (with the reason) · `PENDING` (written and verified locally, not applied anywhere shared) · `READY_FOR_HANDOFF` (packet complete) · `APPLIED_UNVERIFIED` · `VERIFIED_IN_TARGET` · `FAILED`

The last three are reported by whoever applied it (user / DevOps), with their evidence; the agent copies them, never asserts them. Details: [05](references/05-applying-states-and-handoff.md).
