# Database Migrations (Alembic + PostgreSQL)

Authoritative standard for designing, verifying, and handing off PostgreSQL schema DDL and data migrations with Alembic. Model and index design follows `backend-postgres`; directory boundaries follow `{{slot:clean-architecture}}`; sensitive data protection follows `{{slot:secure-coding-standards}}`.

## 1. 3-Tier Environment Authority Model (`M2`)

| Environment Tier | Target Database | Who May Execute Migration? | Mandatory Rule |
|---|---|---|---|
| **Tier 1 — Local / Disposable DB** | `localhost`, compose `db-test`, throwaway `app_migration_check` | **Backend Agent** (`code_writer` / `test_runner`) | Runs autonomously to execute the full disposable-DB verification suite (`V1`–`V8` + `pytest-alembic` → `PASS` / `FAIL`). |
| **Tier 2 — Develop (`develop`)** | Shared `develop` database | **Backend Agent (ONLY on explicit User request)** _or_ **DevOps** | Agent **may** migrate `develop` **only when the user explicitly requests/approves it in the current session** (never autonomously). Agent **must** still generate the full Handoff Packet (`migration-handoff.md`). |
| **Tier 3 — Staging & Production (`staging`, `production`)** | Shared `staging` and `production` databases | **Strictly DevOps** (**NEVER the Backend Agent**) | Backend Agent **never** executes schema or data migrations on `staging` or `production`, even if credentials exist in `.env`. Agent generates `migration-handoff.md` for the user to hand over to DevOps. |

## 2. Never-List (`M1`–`M5`, `M14`)

- **Never** run migrations on `staging` or `production` from the agent, or on `develop` without an explicit user command.
- **Never** change schemas via `Base.metadata.create_all()` outside unit fixtures, manual DDL in `psql`/`postgres-mcp`, editing `alembic_version`, or running `alembic stamp` to skip a broken revision.
- **Never** edit or delete a revision already applied to `develop`, `staging`, or `production` — always create a new forward revision.
- **Never** ship an autogenerated revision without reviewing every line, fixing renames (`drop` + `add` = data loss), and adding `SET LOCAL lock_timeout`, `CONCURRENTLY`, and `NOT VALID`.
- **Never** combine `expand` and `contract` in a single revision while running code still reads the old schema.
- **Never** embed connection strings, passwords, or customer PII in revisions, commands, or `migration-handoff.md`.

## 3. 5-Step Migration Workflow & Mandatory Rules (`A1`–`A9`, `B1`–`B8`, `V1`–`V8`)

1. **Inspect Setup & Target Authority** ([01-alembic-workflow-and-revision-rules.md](references/01-alembic-workflow-and-revision-rules.md)):
   - Read `alembic.ini`, `alembic/env.py`, lockfile prefix (`uv run` / `poetry run`), and verify target host identity before running any command (`A1`–`A9`).
2. **Design Zero-Downtime Schema & Data Steps** ([02-safe-schema-changes-and-backfills.md](references/02-safe-schema-changes-and-backfills.md)):
   - Split breaking changes into `1. Expand → 2. Dual-write code → 3. Batched & tenant-scoped Backfill (B1–B8) → 4. Cutover code → 5. Contract`.
   - Enforce `SET LOCAL lock_timeout = '5s'`, `CREATE INDEX CONCURRENTLY` inside `autocommit_block()`, and `NOT VALID` + `VALIDATE CONSTRAINT`.
3. **Generate & Hand-Review Revision** ([01](references/01-alembic-workflow-and-revision-rules.md)):
   - Run `alembic revision --autogenerate -m "<imperative summary>"`, keep revisions self-contained (`sa.table` instead of importing app models, `A5`), and write a real `downgrade()` (`A6`).
4. **Verify on a Disposable Database (`V1`–`V8` + `pytest-alembic`)** ([03-verification-states-and-handoff.md](references/03-verification-states-and-handoff.md)):
   - Prove clean install, single head, zero drift, upgrade over seeded multi-tenant data, backfill invariants (`= 0`), reversibility (`downgrade -1 && upgrade head`), zero `INVALID` indexes, and `pytest --test-alembic`.
5. **Generate DevOps Handoff Packet (`migration-handoff.md`) & Record State** ([03](references/03-verification-states-and-handoff.md), [templates/migration-handoff.md.tpl](templates/migration-handoff.md.tpl)):
   - Populate `migration-handoff.md` with: (1) **Summary of Changes & Why**, and (2) **Step-by-Step Schema & Data Migration Runbook for DevOps across `develop`, `staging`, and `production`**.

## 4. Disposable-DB CLI Verification Gates (`PASS` / `FAIL`)

| Gate | Command (`cwd: backend root`, disposable DB) | Pass Criteria (`PASS` / `FAIL`) |
|---|---|---|
| **Clean Install (`V1`)** | `uv run alembic upgrade head` | `PASS` on exit `0` (`Running upgrade <prev> -> <new>`) |
| **Single Head & Zero Drift (`V2`)** | `uv run alembic heads && uv run alembic check` | `PASS` when 1 head exists and `No new upgrade operations detected.` |
| **Reversibility (`V5`)** | `uv run alembic downgrade -1 && uv run alembic upgrade head` | `PASS` when both directions exit `0` |
| **Automated Migration Suite (`V8`)** | `uv run pytest --test-alembic -q && uv run pytest tests/<area> -q` | `PASS` when all migration and affected behavior tests pass |

Canonical Migration States: `NOT_REQUIRED` · `PENDING` · `READY_FOR_HANDOFF` · `APPLIED_UNVERIFIED` · `VERIFIED_IN_TARGET` · `FAILED`. Reviewer findings use **`BLOCKER` / `MAJOR` / `MINOR`** ([03](references/03-verification-states-and-handoff.md)).
