# OpenAPI snapshot and diff

Detail for [api-contract-design](../SKILL.md) CT7 and CT9.

## 1. Where the snapshot lives

| Location | When | Content |
|---|---|---|
| `.superpowers/work-items/<slug>/vN/contracts/openapi.json` | Always, for every item that adds or changes an endpoint | Snapshot generated from the revision named in the change record |
| `.superpowers/work-items/<slug>/vN/contracts/openapi.base.json` | When the item changes existing endpoints | Snapshot of `BASE_REVISION` |
| `.superpowers/work-items/<slug>/vN/contracts/contract-change.md` | With every snapshot | The classified diff (Endpoint, Method, Change Class, Reason) |
| The repository's committed contract file (for example `openapi.json` or `docs/openapi.json`) | Only when the workspace already commits one: find it with `git ls-files \| grep -iE 'openapi[^/]*\.(json\|ya?ml)$'` | Updated in the **same task** that changes the endpoint, generated by the same command |

Reason: the handshake keeps project contracts as revisioned artifacts under the work item's `contracts/` folder; a repository copy, when the team keeps one, must never disagree with the code of the same commit. Adding a committed snapshot to a repository that has none is a `D-NN`, not a side effect of a task.

## 2. Generate

1. Runner: `uv.lock` → `uv run`; `poetry.lock` → `poetry run`; otherwise the project's virtualenv interpreter. Record which one.
2. App import path: from the run command (`uvicorn app.main:app`, `fastapi run app/main.py`), the Dockerfile, Procfile or README. If the app is built by a factory (`create_app()`), call it.
3. Prefer a script the workspace already has (`scripts/export_openapi.py`, a `make openapi` target). Otherwise:

```bash
# cwd: service root
uv run python -c "import json,sys; from app.main import app; json.dump(app.openapi(), sys.stdout, indent=2, sort_keys=True); print()" \
  > .superpowers/work-items/<slug>/vN/contracts/openapi.json
```

- `sort_keys=True` and a fixed indent make the diff show only real changes.
- `app.openapi()` does not run the lifespan and opens no database connection, but importing the app loads settings: required settings come from the workspace `.env` (dev/test values). A failed import is `BLOCKED` with the error text, never replaced by a hand-written file.
- Fetching `/openapi.json` from a running service gives the same document; use it for a deployed environment and record the environment and its revision.

## 3. Base snapshot without changing the git state

```bash
# repository commits a contract file
git show <BASE_REVISION>:<path/to/openapi.json> > .superpowers/work-items/<slug>/vN/contracts/openapi.base.json

# otherwise: export the base tree to a scratch folder and generate there with the service's interpreter
mkdir -p <scratch>/base && git archive <BASE_REVISION> | tar -x -C <scratch>/base
cd <scratch>/base && <service-root>/.venv/bin/python -c "import json,sys; from app.main import app; json.dump(app.openapi(), sys.stdout, indent=2, sort_keys=True); print()" \
  > <service-root>/.superpowers/work-items/<slug>/vN/contracts/openapi.base.json
```

Reason: `git archive` reads the commit without checking it out, so the working tree and branch stay untouched. If the dependencies changed between the two revisions, note it in the change record.

## 4. Diff and classify

```bash
# inventory of operations: method, path, operationId, statuses, security
jq -S '[.paths | to_entries[] | .key as $p | .value | to_entries[]
  | {op: "\(.key | ascii_upcase) \($p)", id: .value.operationId,
     statuses: (.value.responses | keys), secured: (.value.security != null)}]' openapi.base.json > ops.base.json
jq -S '...same filter...' openapi.json > ops.new.json
diff -u ops.base.json ops.new.json          # operations added, removed, changed
diff -u openapi.base.json openapi.json      # schema-level detail
```

- If the workspace already has `oasdiff` (`command -v oasdiff`) and it reads the document's OpenAPI version (FastAPI emits 3.1), `oasdiff breaking openapi.base.json openapi.json` lists breaking changes automatically; still classify each line in the change record. Do not install a new tool inside a task (SC10).
- Every diff hunk gets a row in `contract-change.md`: what changed, additive or breaking per [compatibility](compatibility.md), the `D-NN` / task that planned it.
- A hunk no task planned is a defect (`CODE_WRONG`) or a `plan-change-request` (`PLAN_WRONG`); never accept it by regenerating the snapshot.

## 5. Evidence row

| Check | Command | cwd | Result |
|---|---|---|---|
| Snapshot generated | the generate command | service root | exit 0, file path, revision `<sha>` (never `+dirty`) |
| Diff classified | `diff -u ops.base.json ops.new.json` | `contracts/` | N additive, M breaking, each row planned |
| Security coverage | the `jq` security query in SKILL §4 | `contracts/` | Only the endpoints listed as public in `design.md` |

The Code Reviewer reruns the generate command on `REVIEW_REVISION` and compares byte-for-byte with the hand-off snapshot. A mismatch means the snapshot is stale or the tree is dirty: `CHANGES_REQUESTED`.
