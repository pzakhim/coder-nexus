## Frontend rules

- **Frontend scope**: This workspace is a Frontend Client. Own UI/UX & screen expectations from Figma or HTML sitemap specs (`figma-intake`) and the API business contract (`BE_API_READY` vs. `MOCKOON_MOCKED`). **NEVER** modify backend files, databases, or remote server code.
- **Stage 1A frontend intake pillars** (in addition to the PO / BA Requirements Source):
  - **UI Screens, UX Flow & Design System Source**:
    - **Figma (`FIGMA_PROVIDED`)**: A Figma frame linked in the Huly ticket or user prompt is fetched by `task-detail --download` (or `coder-nexus figma fetch <url>`) into `.superpowers/sources/<ISSUE-ID>/figma/` as file-level `tokens.json` (W3C DTCG), frame-level `<node>.spec.json` (`screens[*].tree`, `components`, `workflows_hint`), per-screen `<node>-SNN.png` renders, `<node>.summary.md`, and raw `<node>.json` when the Client `.env` has `FIGMA_TOKEN`; its source status is `READ`, `NOT_PROVIDED` (no token/link) or `UNREACHABLE` (401/403/404).
    - **Interactive HTML Sitemap (`HTML_SITEMAP_PROVIDED`)**: An interactive HTML UI/UX sitemap attached in Huly (auto-indexed up to 150 MB) or manually placed by the user at `.superpowers/sources/<ISSUE-ID>/` (when oversized or local) is unpacked via `coder-nexus sitemap extract` into `.superpowers/sources/<ISSUE-ID>/sitemap/` (`index.md`, `index.json`, and filtered in-scope `screens/*.png`, `*.spec.json`, `*.md`). Never read raw multi-MB `.html` directly.
    - Only `READ` visual sources count as visual input. Follow `figma-intake`: extract `S-NN` and `W-NN` for `FIGMA_PROVIDED` or `HTML_SITEMAP_PROVIDED` **before drafting `1B`** so actors/BRs/screens aren't drafted twice; if no external design is provided (`CODEBASE_ONLY`), treat as a minor edge-case adjustment on an existing screen (`CHANGED`); if a provided visual source fails (`UNREACHABLE`), queue a `Q-NN` (for oversized Huly files, give the user the exact manual-drop path in plain chat) and never fabricate screens or HTML mockups.
  - **Backend API Integration Source (Binary Check: Does BE API Exist Yet?)**:
    - **Case 1 — BE API Exists (`BE_API_READY`)**: Record the API specification source in `codebase-notes.md` so `planning` consolidates it in `design.md` and `PHASE-00` (`[INFO_NOTE]`).
    - **Case 2 — BE API Does Not Exist (or Missing Endpoints) $\to$ Use Mockoon (`MOCKOON_MOCKED`)**: Lock in the business Input/Output contract in `requirements.md` and `codebase-notes.md` (`## 4. Constraints & External Integrations` & `## 5. Extended Rule Details`) per `shared_contracts/api_handshake_protocol.md`. Downstream, `planning` agrees with the user on the `Mockoon Trigger & Test Data Table` in `design.md` and marks `PHASE-00` (`phases/phase-00-prepare.md`) as `[EXECUTE]`.
- **Stage 1A-UX & 1B**: Extract Figma `<node>.spec.json` / `<node>.summary.md` or HTML sitemap `sitemap/screens/*.spec.json` / `*.md` UI flows first, cross-check against provided/estimated APIs and existing Client flows, and populate `## Screens & Visual Sources` (`S-NN`) and `## Workflows` (`W-NN`) in `requirements.md`.
- **Grill dimensions**: The "observable states" dimension covers the Happy Path, **4 Visual States** (`Default/Content`, `Loading`, `Empty`, `Error`), and Multi-Screen state lifecycle.
- **API Boundary**: `spec_writer` owns the business Input/Output of APIs (`BE_API_READY`, `MOCKOON_MOCKED`, or `NONE`) and business Pass/Fail scenarios. `planning` owns the `Mockoon Trigger & Test Data Table`, `PHASE-00` (`phase-00-prepare.md`), and the FE Data Pipeline (remote data access, models, repositories, use cases, and DI).
- **UI / UX & UI Kit Boundary**: `spec_writer` owns screen (`S-NN`) & UX workflow (`W-NN`) requirements and the 4 visual states (`Default/Content`, `Loading`, `Empty`, `Error`). `planning` owns architecture profile resolution, auditing Figma `tokens.json` & `<node>.spec.json` or HTML sitemap `sitemap/screens/*.png` & `*.spec.json` against the codebase UI Kit (`{{slot:ui-kit-mapping}}`), exact widget/component mapping (`C-NN` / `Core gap`), screen base, `Router`, and state contracts in `design.md` (Gate 2).
- **`requirements.md` §4**: Name it `## 4. Behavioral Scenarios & Visual States` and include the 4 Visual States.
