# Work-item contract

Classify the independently accepted **outcome**, not file count or code area. One primary `Type`: `feature`, `bugfix`, `refactor`, `optimization`, `migration`, `maintenance`, `investigation`, `documentation`. Tests and docs supporting a feature stay in that item. Independently valuable outcomes use linked items. Record type, risk and uncertainty separately.

New versions live at `.superpowers/work-items/<slug>/vN/`. Never overwrite a closed version. Link historical `docs/features/` or `.agents/plan` paths as read-only sources. A later version compares the approved contract with actual code and evidence; do not assume an old design shipped.

`requirements.md` and `codebase-notes.md` (authored by Spec Writer via `grill-me`; `brief.md` remains supported for small phase-free items) establish the Gate 1 contract:
- `requirements.md` is the **human-facing specification** ($\le \sim 120$ lines, pure business/UX language, zero code/class names, zero `Option A / Option B` or `Open Questions` sections): Scope & Alignment (`Scope in` / `Scope out`), Actors & Permissions, Business Rules (`BR-NN` citing `D-NN`), Behavioral Scenarios & 4 Visual States (`Given-When-Then`), Acceptance criteria (`AC-NN`), and Gate 1 approval.
- `codebase-notes.md` is the **permanent agent-facing Single Source of Truth** retained throughout the entire `vN/` lifecycle: `## 0. Question Queue (Q-NN)` (must have 0 `OPEN` rows before Gate 1 or Gate 2 approval), `## 1. Decision Log (D-NN)` (recording every confirmed user choice and options considered), `## 2. Glossary`, `## 3. Verified Baseline Facts & Cross-Agent Notes`, `## 4. Constraints & External Integrations`, `## 5. Extended Rule Details`, and `## 6. Change Log`. Only `spec_writer` and `planning` write `codebase-notes.md`; all other agents read it.

`design.md` (authored by Planning via `{{slot:architecture-design}}` + `grill-me`) establishes the technical architecture in one straight locked-in line across the 7 architectural pillars (architectural decision citing `D-NN` in `codebase-notes.md` without `Option A / Option B` sections, Clean Architecture directory tree, screen base/routing, state machine, API mocking, UI Kit discovery, and UX error/storage policies). A feature's Gate 2 approval covers this exact technical architecture specification while retaining `codebase-notes.md` permanently.

`implementation-plan.md` (authored by Planning via `planning-and-task-breakdown`, required for a feature, optional for other types) maps AC → task/phase → decisive check, names dependencies, file ownership, actual Client commands/targets and recovery where relevant. Create `phases/phase-NN-<behavior>.md` only when later deliverables depend on a separately checked result. Each phase has an outcome, inputs/outputs, bounded files, owner, AC IDs, ready condition and pass gate. A feature's Gate 3 covers the plan **and all linked phase revisions**. A small non-feature work item may keep tasks/checks in `brief.md` or `requirements.md` and skip plan/phases; record why. Legacy `validate_plan_slices` requires the versioned feature format and is not proof that a generic brief is approved.

Use `as-built.md` for implemented code and `verification.md` for findings/docs-only evidence as needed. Reviewer reports go under `vN/reviews/` and test/visual evidence under `vN/evidence/`; never write run output into `.agents/`, which holds only synced configuration. Record exact revision, command/target, result and data provenance. Status progresses only on actual evidence; a planned or unavailable check is not `PASS`.

For a phased work item, retain the next-phase handoff in `as-built.md` after each completed phase. The coordinator asks the user whether to continue and waits for an explicit answer before starting the next phase, even when Gate 3 approved the whole plan. On resumption, compare the saved revisions and dependencies with the current Client; a changed contract requires the affected approval or check again.
