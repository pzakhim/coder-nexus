# Client work items

New work belongs in `${workspaceFolder}/.superpowers/work-items/<slug>/vN/` in Client Git. Read [the work-item contract](references/work-item-contract.md), then only the selected row in [type sequences](references/type-sequences.md). Historical `docs/features/` versions remain readable; do not migrate or rewrite them. Plugin files are guidance, not a runtime orchestrator. The host coordinator assigns agents, asks the user, records real approvals and updates execution evidence.

Render only needed artifacts from [requirements](templates/requirements.md.tpl), [codebase-notes](templates/codebase-notes.md.tpl), [brief](templates/brief.md.tpl), the design template of `{{slot:architecture-design}}`, [plan](templates/implementation-plan.md.tpl) and [phase](templates/phase.md.tpl). Resolve every placeholder from real sources before asking for approval; skip optional files instead of creating empty sections.

For UI tasks, Planning classifies destinations using the screen contract in `{{slot:clean-architecture}}` and records the stack's foundation profile (`architecture_profile.mode` where the stack defines one, see `{{slot:core-usage}}`) with evidence in design (brief for phase-free work). Missing an API actually required by the approved profile is `BLOCKED`. Carry the selected profile and applicable routing/lifecycle checks through each handoff.

## Route

1. **Spec Writer (Technical BA):** follow the canonical order in the `spec_writer` agent §3 (1A sources → 1A-0 job type → 1A-G goal + sufficiency → 1B draft → 1A-UX designer → 1C remaining questions → Gate 1); the goal question carries the sufficiency summary and later questions follow `grill-me` §2.2 order with `câu i/N`. Classify the outcome, run **1A Source Intake** followed by **1A-G Goal Framing** (source inventory incl. unreachable PO docs/PDFs, 1–3 outcome goals confirmed by the user as the first question, recorded in `requirements.md` → `## 0. Goals`; every later question, BR, AC, design element and phase serves a goal — see `feature-planner` → `references/03_goal_framing.md`), then (confirm PO/BA source, design-export `.md` UI/UX & design system source, and binary BE API check: `BE_API_READY` vs. `MOCKOON_MOCKED`), **1B Gap & Flow Analysis** (detect API count/schema gaps and current business flow adjustments, and immediately draft `requirements.md` (`Status: DRAFT`) + `codebase-notes.md` with `OPEN` `Q-NN` rows in `## 0. Question Queue (Q-NN)`), and **1C Interactive Open Questions** via `grill-me` + `ask_question` (**1 question at a time**, putting `(Recommended)` first, allowing user counter-questions, consulting `planning` / `code_writer` for out-of-scope technical questions without guessing, and closing each confirmed `Q-NN -> CLOSED -> D-NN` in `codebase-notes.md` while updating `requirements.md`) until `0 OPEN Q-NN` remain; features also require `design.md` (authored by Planning at Gate 2), while other types use it when needed. Feature Gate 1 approves the exact `requirements.md` and `codebase-notes.md` (or `brief.md` for small phase-free items) revision. Returns `READY_FOR_PLANNING` after Gate 1 approval and the item branch from `git-preflight` (spec written first, uncommitted; branch created after Gate 1 from the base the job type needs; the spec is its first commit).
2. **Designer (UI/UX) — only for items with UI impact:** after 1A-G, Spec Writer decides whether the item changes something the user sees (a screen, step, field, message or state is added, changed or removed). If it does, Designer confirms the workflows (`W-NN`) with the user, draws `design-uiux/` with skill `ux-mockup` and `{{slot:ux-kit}}`, iterates and asks the user to approve the exact `uiux.md` revision (`validate_ux_design` without ERROR). Returns `READY_FOR_SPEC` (approved revision), `SKIPPED` (no UI impact, with reason) or `BLOCKED`. Spec Writer maps every `W-NN` into `requirements.md` → `## Workflows`; Gate 1 approves `requirements.md` together with that `uiux.md` revision. The approved revision is the Visual AC for planning, review and verification.
3. **Planning (Tech Lead / Architect):** consume approved `requirements.md` and `codebase-notes.md`. Owns two distinct technical deliverables:
   - **Gate 2 (Architecture Approval):** When `design-uiux/` exists, `design.md` carries `## UI/UX mapping` (each `S-NN` / `C-NN` → screen, route, component); every NEW COMPONENT becomes an explicit task at Gate 3. Perform the Pre-Design Counter-Review & `grill-me` Q&A loop first (queueing any Core gap, architectural trade-off, or Mockoon trigger question as `Q-NN` in `codebase-notes.md`, asking 1 question at a time via `ask_question`, and closing into `D-NN`), then write a decisive, straight-line `design.md` citing `D-NN` across the 7 architectural pillars (architectural decision, Clean Architecture directory tree, screen base/routing, state machine, API integration & Mockoon data design, Core usage + UI mapping, and UX error/storage policies) using skill `{{slot:architecture-design}}`. Retain `codebase-notes.md` permanently throughout the entire `vN/` lifecycle.
   - **Gate 3 (Plan Approval):** For a feature, write `implementation-plan.md`, `phases/phase-00-prepare.md`, and sequential `phases/*.md` (with ordered micro-tasks per phase) using skill `planning-and-task-breakdown`. For non-feature types, return `SKIPPED` when brief/requirements tasks/checks are executable.
4. **Code Writer or Docs Writer:** implement a bounded task or first ready behavior phase using `requirements.md`, `codebase-notes.md`, `design.md`, and `phases/phase-NN-*.md`. Docs Writer owns reader-facing docs and documentation-only items. Do not treat planned code or docs as built.
5. **Code Reviewer:** inspect the same diff and relevant callers, tests and docs; run architecture/analyzer and runtime visual review where applicable (compared with the approved `design-uiux/` revision when it exists). Return actionable findings or an approval tied to revision.
6. **Test Runner:** independently run type-specific checks on the reviewed tree using `requirements.md`, `codebase-notes.md`, and `design.md`. Docs Writer records phase evidence in `as-built.md` from the actual review and test reports; the coordinator checks provenance, records approval references, and owns item status. For findings-only work, use `verification.md` as needed. `NOT_RUN`, `BLOCKED` and `UNVERIFIED` cannot become `PASS`. Any fix invalidates affected review/check evidence.

Use [tool usage](references/tool-usage.md) for the exact conditions, inputs and limits of Hub MCP tools. Use existing `{{slot:clean-architecture}}`, `{{slot:code-review}}`, `{{slot:verification}}` and visual skills only for affected boundaries. Keep Huly read-only and credentials in the Client. No fake business data, APIs, package variants or results.

## Ownership and handoff

| Agent | Writes | Returns |
|---|---|---|
| Spec Writer | `requirements.md`, `codebase-notes.md` (and `brief.md` for phase-free items) | `READY_FOR_PLANNING`, findings-only `READY_FOR_VERIFICATION`, or `BLOCKED` |
| Designer | `design-uiux/` (`uiux.md`, screens, components, mock data, `CHANGELOG.md`) for UI-impact items | `READY_FOR_SPEC`, `SKIPPED`, or `BLOCKED` |
| Planning | `codebase-notes.md` (`D-NN`), `design.md` (Gate 2), `implementation-plan.md` & `phases/*.md` (Gate 3) | `READY_FOR_BUILD`, `SKIPPED`, or `BLOCKED` |
| Code Writer | Assigned Client runtime and test files | `READY_FOR_REVIEW` with full diff scope |
| Docs Writer | Assigned reader-facing docs; phase `as-built.md` after review and tests | `READY_FOR_REVIEW` for reader docs; evidence-backed phase record for coordinator |
| Code Reviewer | `.superpowers/work-items/<slug>/vN/reviews/` report | `APPROVED`, `CHANGES_REQUESTED`, or `BLOCKED` |
| Test Runner | `.superpowers/work-items/<slug>/vN/evidence/` report | Per-AC `PASS`, `FAILED`, `BLOCKED`, or `NOT_RUN` |

Every handoff includes item/version/type, approved document revisions and user response references where required, AC IDs, task or phase, base/review revisions, staged/unstaged/untracked scope, affected files, planned checks, UI target/states, and unresolved blockers. The coordinator alone changes item status and verifies that `as-built.md` matches the underlying evidence. After a UI item is delivered and verified, the coordinator (or Docs Writer when assigned) updates `.superpowers/ux/screen-catalog.md`: NEW → EXISTING, the approved design revision, and the current screenshot. Docs Writer joins before final review when reader-facing docs are part of acceptance; it records the phase's as-built evidence after Test Runner reports.
