# Divergent pass (optional)

Use it when the options you can see are variants of one idea, or when the user asks for alternatives. Skip it when two or three genuinely different options are already on the table. Reason: widening costs time and only pays when the first idea anchors you.

## 1. Widen (working notes only)

Write 4-6 candidates in one line each. Apply the lenses that fit; do not run all of them mechanically.

| Lens | Ask | Typical result |
|---|---|---|
| Inversion | What if we did the opposite of the obvious approach? | Pull instead of push, warn instead of block, the system decides instead of the user |
| Remove a constraint | Which assumed constraint is not a confirmed `D-NN` or verified fact? What if it were gone? | Reveals a cheaper path, or a constraint worth confirming as `Q-NN` |
| 10x simpler | What is the smallest version that still meets every `G-NN`? | Fewer screens, reuse of an existing flow or component, no new contract |
| Audience shift | What if the primary actor were a different role (admin, first-time user, support, another service)? | Different entry point, defaults or permissions |
| Reuse | What does the codebase or app already do that nearly fits? | Extend instead of build |
| Combination | Can two partial ideas merge into one clean option? | A hybrid option |

"Remove a constraint" is a thinking tool only. A candidate that actually breaks a confirmed constraint is dropped, or the constraint itself becomes a `Q-NN` for its owner.

## 2. Converge

1. Drop every candidate that misses a confirmed goal, contradicts a `D-NN`, crosses your ownership (see the mode file), or serves no goal.
2. Cluster the rest; keep the 2-3 that differ most in what the goal owner cares about.
3. Describe them with the fields in [SKILL.md](../SKILL.md#2-build-the-options) and pick your recommendation.

Never show the wide list to the user. Reason: a long menu replaces one decision with many and breaks one-question-at-a-time.
